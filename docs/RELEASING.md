# Releasing LAMISS

How a build of the extension finds its backend, how to make the Chrome Web Store package, and how it gets to
the store. Tracking issue: https://github.com/DanielFuzzy/Lamiss/issues/35.

## 1. Backend endpoints

Every build talks to **one backend origin**. REST calls go to `<apiUrl>/api/...` and the live connection to
`<ws(s)>://<host>/ws/...`, derived from the same URL (`https` gives `wss`). The extension calls no other backend
service: speech and AI run behind that server. The origin is fixed at build time in
`shared/lamiss-config.js`, generated by `scripts/build.js`. No source file contains a backend address.

The addresses live in **`config/environments.json`**:

| Environment | Used for | `apiUrl` rules | Overrides |
|---|---|---|---|
| `development` | `npm run build`, `npm test`, loading `compiled/` unpacked | anything `http(s)://host[:port]` (default `http://localhost:8080`) | `LAMISS_API_URL` and `LAMISS_GOOGLE_CLIENT_ID` from the shell or a git-ignored `.env` |
| `staging` | testers loading a ZIP unpacked, against a staging server | `https://` on a public host | none |
| `production` | the Chrome Web Store package | `https://` on a public host | none |

`googleClientId` is the public client ID of the Google OAuth client (not a secret). It is required for staging
and production. `.env` is never read for staging or production builds, and the build refuses
`LAMISS_API_URL`/`LAMISS_GOOGLE_CLIENT_ID` there, so a developer's local settings can't leak into a release.

**Why there is no runtime or remote configuration.** Manifest V3 grants host permissions at install time, from
the manifest. A backend address downloaded later would have no permission to be called, unless the extension
asked for every site (`<all_urls>`), which the store discourages and users rightly distrust. It would also let
whoever controls that download redirect users' tokens. So moving the production backend means editing
`config/environments.json` and releasing an update: no application code changes.

The extension checks its own configuration before every call (`lamissBackendConfigProblem` in
`src/shared/lamiss-api.ts`). Outside development, an address that isn't `https`/`wss`, or a REST and WebSocket
pair that disagree, is never called, not even with the token. The user sees "This version of Lamiss has no
valid server address". An unreachable server shows the existing "Could not reach Lamiss at …" message.

### Moving the backend, or adding an environment

1. Edit `config/environments.json`: set `apiUrl` (scheme + host + optional port, no path) and `googleClientId`.
   For a new environment, add it there **and** to `ENVIRONMENTS` in `scripts/lib/build-config.js`, plus a
   `package:<name>` script in `package.json`.
2. On the backend, allow the extension's origin: add `chrome-extension://<extension-id>` to
   `LAMISS_CORS_ALLOWED_ORIGINS`.
3. In the Google Cloud console, OAuth client → Authorized redirect URIs: add
   `https://<extension-id>.chromiumapp.org/`.
4. Build and test (sections 3 and 4).

**Extension IDs.** Development and staging keep the manifest `"key"`, so unpacked builds always have the same ID
(the one in `README.md`). The Chrome Web Store rejects packages with a `"key"`: production builds drop it, and the
store item gets **its own ID**, shown in the Developer Dashboard after the first upload. Steps 2 and 3 must
be done for that ID too, otherwise sign-in fails in the store version.

## 2. Versions

`package.json` and `manifest.json` carry the same `version` (`X.Y.Z`, numbers only); the package build refuses
a mismatch. Every store upload needs a higher version than the last one. To release:

```sh
npm version 0.2.0 --no-git-tag-version   # updates package.json
# edit manifest.json "version" to 0.2.0, commit both, merge to main
git tag v0.2.0 && git push origin v0.2.0
```

## 3. Building the production package

```sh
npm ci
npm run package:production     # or package:staging
```

`scripts/package.js` does the following:

1. Rebuilds a clean `dist/production/extension/`: the compiled TypeScript and the static files, configured for
   production. Scripts nothing loads (test-only modules) are left out.
2. Runs `scripts/lib/validate-package.js`. It checks Manifest V3, the name, a description of at most 132
   characters, the version, the icons (real PNGs at 16/32/48/128), the service worker and its imports, the popup,
   content scripts and web-accessible resources. It also checks that every script and style the pages load is
   present and local.
   - **Permissions:** only `scripting`, `webRequest`, `storage`, `offscreen` and `identity`, and no
     all-sites hosts. Every host is `https` and none is local. There is no `"key"` and no loose
     Content Security Policy.
   - **Contents:** only `.js/.html/.css/.json/.png/.svg`, with no `.env`, source maps, `.ts` files or
     `localhost` in the package.
3. Writes **`dist/lamiss-<version>-production.zip`** and its `.sha256`. The ZIP is deterministic (sorted files,
   fixed timestamps), so anyone with the same commit gets the same SHA-256 as the release.

`dist/` is git-ignored. Production and staging fail until their `apiUrl` and `googleClientId` are set.

## 4. Installing locally for testing

- **Unpacked:** unzip the ZIP, open `chrome://extensions`, enable Developer mode, click **Load unpacked** and pick
  the unzipped folder (the one with `manifest.json`). A production ZIP has no `"key"`, so it gets a random ID:
  sign-in then needs that ID in the backend CORS list and the OAuth redirect URIs (section 1). To test a
  release candidate with working sign-in, use `package:staging`, which keeps the fixed ID, or test through an
  Unlisted store release.
- **Development:** `npm run build` and load `compiled/` as before (`README.md`).

## 5. Chrome Web Store: one-time setup

1. **Developer account:** at https://chrome.google.com/webstore/devconsole, sign in with the Google account that
   will own LAMISS. A team or group account is better than a personal one. Pay the one-time registration fee and
   complete the account verification Google asks for (identity, contact e-mail, and for a trader account the
   trader details).
2. **First upload by hand:** **New item**, then upload `dist/lamiss-<version>-production.zip`. This creates
   the item and its **extension ID**. Do section 1, steps 2 and 3, for that ID, then rebuild if anything
   changed.
3. **Store listing, Privacy and Distribution tabs:** fill them from `store/listing.md`, with the images in
   `store/assets/` (re-made with `scripts/store-assets.js`). The **privacy policy URL is required** and does
   not exist yet. See `store/privacy-data-flow.md` (what the extension collects) and
   `store/privacy-policy-draft.md`.
4. **API credentials for the release workflow** (optional; uploading by hand works too):
   1. In a Google Cloud project, enable the **Chrome Web Store API**.
   2. Create an OAuth client and get a refresh token for the scope
      `https://www.googleapis.com/auth/chromewebstore`, signed in as the developer account. The OAuth
      Playground with your own client is the usual way.
   3. In GitHub, go to the extension repo, then **Settings → Environments → New environment
      `chrome-web-store`**:
      - add **required reviewers**, so publishing needs an explicit approval;
      - add the secrets `CWS_CLIENT_ID`, `CWS_CLIENT_SECRET` and `CWS_REFRESH_TOKEN`;
      - add the variable `CWS_EXTENSION_ID` (the item ID).
   4. Never commit them anywhere. `scripts/cws-publish.js` reads them only from the environment.

## 6. Releasing

### Unlisted (beta), the first release
1. Tag `vX.Y.Z` (section 2). The **Release** workflow tests, packages and validates, then attaches the ZIP to a
   **draft** GitHub Release.
2. In the dashboard, set **Distribution → Visibility: Unlisted**.
3. Either upload the ZIP by hand and click **Submit for review**, or run **Actions → Release → Run workflow**
   with `production`, **Upload to the Chrome Web Store** and **Submit for review** checked, and target `default`.
   The upload job then waits for a reviewer to approve it in the `chrome-web-store` environment.
4. Google reviews it, from hours to several days. Once approved, anyone with the item's link can install it.
   Share the link with testers.

### Public
When the beta is done: in the dashboard, set **Visibility: Public** and save. That is a review too. No new
package is needed unless the code changed.

### Later updates
Bump the version, tag, and either upload by hand or run the workflow as above. Installed copies update
themselves within hours of approval.

`trustedTesters` publishes only to the testers listed in the dashboard, and is an alternative to Unlisted
for a closed beta.

**Status:** `scripts/cws-publish.js` uses Chrome Web Store API **v1.1**. It is unit-tested against a fake API
but has **not yet run against a real item**, because there were no credentials. Run it once with only
**Upload** checked (no submit) and check the draft in the dashboard before trusting it. If Google has
moved to a newer API version, update the URLs at the top of the script.

## 7. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `no apiUrl for "production"` | Set `environments.production.apiUrl` (and `googleClientId`) in `config/environments.json`. |
| `LAMISS_API_URL … can only override development builds` | Unset the variable for staging/production builds. Those come only from the file. |
| `apiUrl must use https:// outside development` / `must be a public host` | Staging and production need TLS on a public name. Put the backend behind HTTPS (a reverse proxy or the host's TLS). |
| Package validation fails | The message names the file or field. Fix it in the source or manifest, never in `dist/`. |
| Store: "key field is not allowed" / "manifest is invalid" | Upload a `package:production` ZIP, not `compiled/` or a staging ZIP. |
| Store: version must be greater | Bump `package.json` and `manifest.json` (section 2). |
| Sign-in fails in the store version (`redirect_uri_mismatch`) | Add `https://<store-id>.chromiumapp.org/` to the OAuth client (section 1). |
| Every call fails with CORS errors in the store version | Add `chrome-extension://<store-id>` to the backend's `LAMISS_CORS_ALLOWED_ORIGINS`. |
| "This version of Lamiss has no valid server address" | The package was edited after the build, or built wrongly. Rebuild with `npm run package:production`. |
| Release workflow: `tag … does not match version` | Tag `v` + the exact `package.json` version. |
| Release workflow: `CWS_… is not set` | Add the secret or variable to the `chrome-web-store` environment (section 5). |
| `could not get an access token (invalid_grant)` | The refresh token was revoked or expired. Create a new one (section 5). |
| Rejected in review for permissions | Paste the justifications from `store/listing.md`. Don't add permissions the validator doesn't allow. |
